# 档案馆门口接待机方案

## 目标

在档案馆门口放一台 PC，浏览器全屏运行接待页面，访客可通过文字或语音提问，系统基于知识库回答，并以语音和数字人形式反馈。

## 当前方案

不再把 Fay 作为 kiosk 主线，当前采用：

- 自定义网页
- 轻后端编排层 `kiosk_app`
- 现有模型服务复用

角色分工：

- `136`：HTTPS 入口与导航
- `148`：kiosk 页面与后端编排
- `153`：ASR / LLM / TTS / 数字人

## 当前线上入口

- 正式入口：`https://avata.nbdag.lan`

## 当前链路

```text
浏览器
  -> kiosk_app
  -> FunASR
  -> RAGFlow
  -> Ollama
  -> CosyVoice
  -> metahuman-stream
```

## 当前主要问题

### 1. 数字人已有画面，但嘴部发糊

这已经不再是“完全没播”的问题，而是 `153` 上数字人虽然出画面并能说话，但嘴部观感不佳。

已确认过两个层面的问题：

- 旧问题：
  - 文本推送到了 `humanchat`
  - 该路由会触发数字人内部 LLM
  - 容器缺 `openai` 依赖，导致失败
- 已修掉的问题：
  - `LipReal` 没有初始化 `self.tts`
  - `tts='cosyvoice'` 缺初始化分支
  - `CosyVoice` 原始 PCM 被误按 WAV 解析
- 当前剩余问题：
  - 当前演示 avatar 来自静态图片，不是真人说话视频源
  - `wav2lip` 本身是局部嘴部重绘，嘴部容易出现发糊感
  - `153` 上 `Ollama / CosyVoice / rerank-service / metahuman` 同机争抢 `Tesla T4 15GB`
  - 显存紧张时，`metahuman` 甚至会让 `/offer` 间歇性失败

结论：

- 现在主问题已经从 kiosk 页面转移到 `153` 的渲染质量和算力预算。

### 2. RAGFlow 偶发失败

- 之前部分“未命中知识库”其实是误判。
- 已抓到真实上游错误：
  - `cudaMalloc failed: out of memory`
- 所以接待机要区分：
  - 真未命中
  - 检索失败

### 3. 语音链路仍需完整回归

- HTTPS 录音权限问题已经解决。
- `voice-chat` 代码链路也已经在 `kiosk_app` 中落地。
- 但还需要再做一轮完整真机验证：
  - 录音
  - 识别
  - 问答
  - 语音
  - 数字人播报

## 当前优先级

1. 先解决 `153` 算力竞争，保证数字人稳定占到显存
2. 再观察嘴部发糊是否随算力释放而改善
3. 如果仍不满足，再换真人近景视频源重做 avatar
4. 跑通完整语音闭环
5. 继续观察 `RAGFlow` OOM 条件

## 当前不优先做的事情

- 不回 Fay 主线
- 不上复杂 Agent
- 不做多终端支持
- 不先换数字人框架
